# ADR-001: Local Application Architecture and Data Persistence

## Context

My Food Waste Reducer app needs to let me keep track of food in my pantry and refrigerator. The app also needs to keep grocery-list information and remember my data after the application is closed and opened again.

I needed to decide how my application would be organized and how the data would be saved. Since this is currently a small, single-user Python application, I considered using simple file storage, SQLite, or a larger client-server setup.

The main requirements that affected this decision were that inventory and grocery-list data must be saved between sessions, the app should respond quickly when inventory is changed, and invalid food entries should be rejected.

## The Decision

I decided to build my Food Waste Reducer as a **single Python modular application using SQLite for data persistence**.

I will separate the application into different responsibilities:

- **Domain and validation:** Handles food-item rules and checks that required information is valid.
- **Application services:** Handles actions such as adding, removing, and marking food as used, as well as managing the grocery list.
- **Persistence:** Uses SQLite to save food items and grocery-list information.
- **Presentation:** Handles what I see and interact with in the application.

I will keep the UI and database separate from the main application rules so that changes to one part do not require me to rewrite the entire application.

## Alternatives Considered

### Alternative 1: In-memory storage

I considered keeping the food and grocery-list data only in the application's memory.

I did not choose this because all of the data would be lost when the application closes. This would not meet the requirement that my inventory and grocery-list information remain available when I open the app again.

### Alternative 2: JSON or other flat files

I considered saving the information in JSON files instead of using a database.

I decided against it because my app will need to update, search, and manage different types of information. SQLite gives me a more organized way to handle related data and updates.

### Alternative 3: Client-server application with a hosted database

I considered creating a client-server application with a database hosted online.

I did not choose this because my current requirements are for a single user and do not require accounts, multiple users, or using the app across multiple devices. A hosted system would add extra setup and complexity that my current project does not need.

### Alternative 4: Microservices

I also considered splitting my application into multiple services.

I did not choose this because the Food Waste Reducer is a small application. Having multiple services would make development, testing, and deployment more complicated without providing a clear benefit for my current requirements.

## Consequences

### What This Makes Easier

- My food and grocery-list data can be saved and loaded after I restart the application.
- My app can work without an internet connection.
- SQLite does not require me to set up a separate database server.
- Keeping my application in separate modules makes my code easier to organize and test.
- I can potentially change the database or UI later without completely rewriting my application's main rules.

### What This Makes Harder

- My data is stored only on my computer, so it is not automatically available on another device.
- My application does not automatically provide cloud backups.
- If I later need multiple users or cross-device synchronization, I will need to expand the architecture.
- I still need to choose and implement the specific user-interface framework.
- I need to make sure my local database is stored safely so I do not accidentally lose my data.
- Moving to a hosted database in the future would require additional development.

I accepted these trade-offs because my current project is designed for a single user and does not require online synchronization or multiple users.

## Revisit When

I will reconsider this decision if my requirements change to include multiple users, accounts, cross-device synchronization, cloud backups, or other features that require a networked backend.
